# Data architecture and privacy

Status: proposed contracts. Choose and test the persistence implementation before calling the ledger complete.

## Separation

Public repository: generic application code, educational content, source metadata, tests, and documentation.

Browser-local state: a user's learning notes, quest events, questions, and correction drafts. This data is never part of a build, analytics payload, issue, or commit.

Private instance: identifiable child records and monitoring, in a separate repository, storage boundary, and deployment. Public code must work without knowing whether a private instance exists.

Copy shared code in one direction, from the approved public code into a private instance. Keep data and configuration separate. Never copy the private build output or complete working directory back to public.

## Proposed content records

| Record | Essential fields |
| --- | --- |
| Area | Stable ID, label, description, ordering, source references |
| Strand | Stable ID, area ID, label, developmental context |
| Activity | Stable ID, strand ID, title, purpose, source references, version, review status |
| Connection | From ID, to ID, relationship type, explanation, supporting source, review status |
| Source | Stable ID, title, URL, publisher, source type, checked date |
| Quest | Stable ID, activity/area reference, purpose, adult task, reflection prompt, version |

Relationship types include related, prepares-for, extends, and revisits. Do not infer prepares-for from display ordering. Source-specific relations may conflict; show the provenance rather than silently resolving them.

Review statuses: draft, source-checked, educator-reviewed, superseded. Source-checked does not imply expert review or organizational endorsement.

## Proposed ledger event

Fields: schema version, random event ID, event type, recorded-at timestamp, optional event date, area/activity/quest reference, content version, text, optional source references, and optional relates-to event ID.

Do not require a real name, email address, birth date, or organization to use a local ledger. Timestamps are generated by the client and are not independently verified. Derived views must preserve the original events.

Correction rules:

- A correction adds an event referencing an existing event or an educational content version.
- An ordinary user correction cannot alter official content or a private imported record.
- Invalid or missing references must be visible as unresolved, not silently attached elsewhere.
- Duplicate event IDs during restore must be reconciled or rejected, not silently overwritten.
- Accepted curriculum changes create a new content version so earlier notes retain their context.

## Security baseline for the public app

Use a static, dependency-light first release with browser-local persistence. Prefer no network calls other than fetching the app's own public assets. Source links are explicit user navigations. No analytics, remote fonts, external scripts, or advertising by default.

Render all ledger content as text, never executable HTML. Validate restored JSON for shape, types, lengths, timestamps, and references. Restrict navigable source URLs to supported HTTPS URLs. Protect against oversized files and prototype-pollution keys. Never evaluate imported content.

Browser storage and downloaded exports are not automatically encrypted. Describe the actual behavior. Do not market the ledger as confidential against another person using the same device or against malicious browser extensions.

The public commit checker is heuristic and must be paired with diff review. Local hooks require installation on each checkout and can be bypassed. CI runs after code reaches GitHub, so it is a secondary control, not a substitute for pre-commit review. Branch protection is not assumed to be configured.

## Hosting

GitHub Pages is a candidate for the public static app after the first working increment and deployment tests. A private repository must never be treated as proof that its website is private. A child-specific deployment requires a separate access-control design and verification before publication.

No hosting, account system, cloud ledger synchronization, or public correction submission is implemented by this design increment.

## Private deployment release gate

Before a child-data service is deployed: threat model, authenticated access, authorization per record, encryption in transit and at rest, secure session handling, recovery and deletion policies, least-privilege credentials, no public data in static assets, and tests proving unauthenticated access is rejected. Do not claim end-to-end encryption unless key management and the complete data path actually provide it.
